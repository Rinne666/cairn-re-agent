# Real Pi Worker Closed-Loop Design

## Goal

Prove the existing `Graph → Context → Pi → Structured Output → Graph` path with the real local Pi CLI, without adding reverse-engineering tools or changing the frontend.

## Design

- Keep `Graph Engine → Worker Protocol → AgentDriver → PiDriver`. Graph services depend only on the protocol/driver boundary; Pi command flags, prompt, JSON event parsing, retry, and usage extraction stay inside `PiDriver`.
- Define all `WorkerOutput` fields as required with exact names/types: `observations: list[WorkerFinding]`, `evidence: list[WorkerFinding]`, `hypotheses: list[WorkerFinding]`, `facts: list[WorkerFinding]`, `relations: list[WorkerRelation]`, `artifacts: list[WorkerArtifact]`, `suggested_intents: list[SuggestedIntent]` (max 3), `status: Literal["completed", "failed"]`, and `summary: str`. `WorkerFinding` has non-empty string `kind`, `label`, and `entity_key`, object `properties`, and `confidence: float` in `[0,1]`; category list items must have matching kinds (`Observation`, `Evidence`, `Hypothesis`, `Fact`). `WorkerRelation` has non-empty string `source_entity_key`/`target_entity_key`, object properties, and kind exactly one of `derived_from`, `supports`, `contradicts`, `verified_by`, `references`, `calls`, `flows_to`. `WorkerArtifact` mirrors the existing Artifact write contract: non-empty `kind`, `path`, `sha256`, and `summary`; nonnegative integer `size`; object `provenance` (Pi receives no tools, so this list is expected to be empty). `SuggestedIntent` has non-empty `description`, `source_entity_keys: list[str]` containing only strings, and `goal_relevance`, `information_gain`, `confidence`, `expected_cost` each `Literal["low", "medium", "high"]`. Reject missing/extra fields, duplicate finding keys, and invalid values.
- Context assembly includes the local graph nodes **and their connecting relations** (source/target entity keys, kind, properties), alongside goal, intent, existing facts/evidence/hypotheses, budget, and `available_tools=[]`. Graph Engine owns semantic validation and atomic graph application; `PiDriver` owns process parsing and Pydantic validation. The `AgentDriver` boundary returns only `WorkerOutput` plus generic run telemetry/diagnostics, never Pi session/model/tool objects.
- Run Pi headlessly with no session, tools, extensions, skills, prompt templates, or project context files. The system prompt asks for JSON only, distinguishes Observation/Evidence/Hypothesis/Fact, forbids unsupported Facts, forbids graph-completion speculation, and limits suggested intents.
- Extract Pi's final assistant text and token usage inside `PiDriver`; validate the text with Pydantic. Retry exactly once only when the model response fails Pydantic validation. Do not strip Markdown or repair JSON. On Windows, resolve the npm `.cmd`/`.ps1` shim to its Node entrypoint and launch `node.exe` with an argv list; if the shim cannot be resolved, fail clearly and allow an explicit `node <entrypoint>` command. Preserve argument boundaries for paths with spaces.
- Validate every relation endpoint against a returned finding or an existing node in the same project before semantic mutation. Require each returned Fact to have an explicit outgoing `verified_by` relation to an Evidence node (returned or existing). Apply findings, explicit Worker relations, and suggested intents atomically. A Pi process error, invalid output after retry, unresolved relation, unsupported Fact, or well-formed `status="failed"` changes no semantic nodes, edges, or suggested intents. Database errors roll back graph application first, then persist a failed run/intent where the database is available.
- Commit the claimed/running run before starting Pi. A heartbeat task uses separate short-lived DB sessions every `min(30 seconds, lease_duration / 3)` to extend `heartbeat_at` and `lease_until`; it stops on process completion. If renewal fails or ownership is lost, cancel the child process and fail the run. The `WorkerRun` and `Intent` terminal status matches `WorkerOutput.status`; `Worker.status` returns to operational `idle` and `Worker.metadata.last_run_status` records the outcome.
- Reuse existing `WorkerRun` columns; put schema/retry/count/duration/duplicate/unsupported-fact metrics and failure diagnostics in JSON `output_summary`, with token counts in existing columns. No schema migration. `schema_valid` means the final model response passed Pydantic; `retry_count` is extra Pi calls (0 or 1); tokens and duration sum all attempts. Schema-invalid-attempt rate is invalid Pydantic responses / all Pi calls. Duplicate-intent rate numerator is suggested intents found to already exist by the existing dedupe key (including repeats within the same output); denominator is all suggested intents. Unsupported-Fact rate is rejected unsupported Facts / all returned Facts; zero when no Facts are returned. Counts are the final parsed output counts, or zero when no output validates.
- Provide a CLI validation entry point that seeds a fresh isolated local demo project using the existing `seed_demo` graph/goal, runs exactly 20 sequential real Pi WorkerRuns with `available_tools=[]`, and creates one uniquely numbered continuation intent only when the prior output leaves no claimable Pi suggestion. Run it from the isolated worktree's `backend` directory; the relative DB is the ignored `backend/cairn.db`, and each invocation creates a fresh demo Project without deleting prior data. Record the experiment/project IDs, DB path, Pi CLI version, effective provider/model, timestamps, and 20 WorkerRun IDs for reproducibility.
- The experiment succeeds only if 20/20 persisted WorkerRuns are completed with `schema_valid=true`, matching completed Intent and WorkerOutput state, no unresolved relations, no unsupported Facts, and no duplicate graph/intent rows. Success rate denominator is exactly 20 WorkerRuns. Schema-invalid-attempt rate is invalid Pydantic responses / total Pi invocations (20 plus retries). Unsupported-Fact rate is rejected unsupported Facts / all returned Facts. Duplicate-intent rate numerator is suggestions already present by dedupe key, including repeats within the same output; denominator is all suggestions. Report aggregate `token_input` and `token_output` totals and per-run means, plus total and mean duration. For reproduction, record Pi CLI version, provider/model, budget, prompt SHA-256, schema SHA-256, database path, experiment/project IDs, and WorkerRun IDs. The report must reconcile all totals/rates with these 20 persisted rows. Duplicate suggestions are reported and must be deduped by the existing unique intent key.

## Failure behavior

Pi process errors, exhausted schema retry, unsupported Facts, unresolved relations, or `status="failed"` produce a failed WorkerRun and failed Intent; preserve raw stdout/stderr and do not ingest findings/relations/intents. A well-formed `status="failed"` is not retried. Validation precedes every semantic graph write.

## Validation

Test the full required schema and its invalid variants, Windows Pi process invocation, output parsing/retry/failure, local graph context relations, explicit-only relation ingestion, graph non-mutation on every failure path, intent dedupe, lease renewal/loss/cancellation, and state consistency. Then run 20 actual Pi calls and reconcile persisted WorkerRuns against the report. Report success/schema-invalid/unsupported-Fact/duplicate-intent rates, tokens, duration, observed failures, protocol weaknesses, and whether the architecture is ready for Ghidra integration (only the Worker boundary, not Ghidra itself, is in scope).
